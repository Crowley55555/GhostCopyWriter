## Порядок исполнения (решение владельца 2026-10-06)

- **Оркестратор** — отдельная сессия Claude Code, которая вела план. Пишет промпт для каждой фазы в `plans/zapusk-demo-prompts/phase-N.md`, проводит ревью результата фазы, сверяет каждое своё замечание с кодом (роль судьи), пишет промпт на исправления, после успешного ревью делает поимённый коммит фазы в `dev`.
- **Исполнитель** — новая сессия Claude Code на каждую фазу и на каждый раунд исправлений. Работает строго по промпту и этому плану, пишет тесты, код и checkpoint, **не коммитит** и не делает push.
- Ревью оркестратора независимо от исполнителя: разные сессии, оркестратор код фазы не пишет. Владелец может оспорить любое замечание.
- Цикл фазы: промпт → исполнитель → ревью → (промпт на исправления → исполнитель → повторное ревью) → коммит → промпт следующей фазы.

## Цель и контекст

- **Для кого и зачем:** Ghostwriter сейчас — демонстрационный проект (портфолио), не SaaS. Потенциальный заказчик разработки открывает ссылку и за пару минут видит, как владельцу малого бизнеса пишется живой пост под VK, Telegram или Дзен — сразу без регистрации или с регистрацией по логину и паролю. Измеримый результат — критерии готовности в `idea/mvp.md` (версия 2).
- **Источники фактов:** `idea/` (ядро, исследование, риски, принципы, MVP; локально, не в git), код репозитория. Бизнес-контекст владельца хранится вне репозитория. Гипотеза: ценность для владельцев бизнеса не проверена (`idea/proof-of-value.md`).
- **Архитектура:** отдельного документа нет; раздел «Архитектура» в `README.md` устарел (Flask, OpenAI, бот) и переписывается в фазе 6.
- **Что уже есть:**
  - Django-приложение с генерацией через GigaChat (`generator/gigachat_api.py`), картинки GigaChat по кнопке.
  - Доступ по токенам `TemporaryAccessToken`: `@token_required`, `@consume_generation`, `TokenAccessMiddleware`, вход по ссылке `token_auth_view`. Токены выдавал Telegram-бот. Middleware не учитывает `request.user`; декораторы при плохом токене делают `session.flush()`.
  - Регистрация и вход отключены (`register_view` → заглушка, `RegisterForm` удалена). Старый `agreement_view` брал пароль открытым текстом из сессии. Шаблоны входа и регистрации ссылаются на `quick_login` (маршрут только при `DEBUG`).
  - Шаблоны: 15 страниц наследуют `generator/index.html` (тема «Киберпанк», применяется после загрузки DOM), `landing.html` — отдельная страница; Bootstrap 5.3.0, иконки и шрифты — с внешних CDN; `styles.css` — 1570 строк.
  - Тесты `tests.test_django_models`, `tests.test_django_isolated`: 21 тест, на 2026-10-06 **8 падений и 3 ошибки**. В `test_settings` миграции отключены, база в памяти.
  - Продакшен: `docker-compose.production.yml` (django, bot, db, redis, nginx), `production_settings.py` с `DEBUG = False`, сессии `cached_db`, самоподписанный сертификат на IP, только порт 443. Сервер не работает. Домена нет — владелец купит.
- **Найдено на ревью версии 1 (код, 2026-10-06), закрывается этим планом:**
  - `DJANGO_API_KEY` не читается в настройках Django, поэтому проверка ключа в API всегда пропускается: любой может создать токен любого типа, включая безлимитный DEVELOPER (`generator/views.py:1456-1463`). Вебхук ЮKassa не проверяет подпись.
  - Перегенерация текста и картинки под `/api/` работает без токена и без CSRF (`generator/views.py:323-324, 581-582`).
  - `get_client_ip` берёт первый элемент `X-Forwarded-For`, который клиент может подделать (`decorators.py:110-113`).
  - Продакшен читает `DJANGO_SECRET_KEY`, а compose передаёт `SECRET_KEY` (`production_settings.py:15`, `docker-compose.production.yml:48`).
  - Стена и детали генераций без пользователя показывают всем анонимные генерации всех посетителей (`views.py:901-933`).

## Решения владельца (2026-10-06)

- Коммиты: разрешены поимённые коммиты в `dev` после ревью каждой фазы. Push — только по отдельному решению.
- Админка остаётся — для наблюдения за квотой; суперпользователя на сервере создаёт владелец.
- Домен владелец покупает у регистратора (например, Reg.ru); сервер может быть у другого провайдера — домен направляется на IP сервера A-записью.
- Регистрация — по логину и паролю, без email. Зарегистрированный получает историю постов, сохранённое «О бизнесе», шаблоны настроек и больше генераций в день. Демо без регистрации остаётся.
- Оформление: тёмная тема по умолчанию и светлая по переключателю; сайт должен выглядеть как нормальный сайт.

- **Перед началом:** `python manage.py makemigrations --check --dry-run --settings=ghostwriter.settings`; найденный дрейф моделей и миграций закрыть отдельной миграцией и отдельным коммитом.
- **Действия (сначала падающие тесты):**
  - **Регистрация — новая форма** на основе `UserCreationForm`: логин, пароль дважды, галочка согласия. Без email. Валидаторы паролей Django. Уведомление на этой же странице: что хранится (логин, хэш пароля, «О бизнесе», посты, технические данные для защиты от злоупотреблений) и зачем; без ссылок на несуществующие документы. Пароль нигде не хранится промежуточно. `agreement_view` и `user_agreement.html` не используются.
  - **Вход** — через `django.contrib.auth.login` (смена ключа сессии). **Выход** — POST-формой. Блоки быстрого входа убрать из шаблонов, маршрут `quick_login` снять.
  - **Правило доступа (в middleware):** если `request.user.is_authenticated`, токен всегда берётся или создаётся по пользователю через общую функцию сессии из фазы 1; демо-токен в сессии игнорируется; для вошедших — без `session.flush()`. `/auth/token/` при активном входе — отказ. `/login/` и `/register/` — в исключениях middleware.
  - **Токен зарегистрированного:** новый тип `REGISTERED` в `tariffs.py`, без OpenAI, `gigachat_tokens_limit=-1`. Ровно один на пользователя: новое поле `user` у `TemporaryAccessToken` (уникальное, `on_delete=CASCADE`, миграция).
  - **Дневной лимит зарегистрированного** — в единой проверке из фазы 1: фактические вызовы пользователя за скользящие 24 часа по `GigaChatTokenUsage.user`, значение из env (больше демо). Планировщик не нужен. Общий дневной потолок действует и на зарегистрированных.
  - **«О бизнесе»** — поле профиля (миграция); подставляется в форму, редактируется в профиле.
  - **Свои данные:** история, детали, удаление генераций и шаблоны — только свои (фильтр по `request.user`, ветка `user__isnull=True` удаляется). Страницы профиля, истории и шаблонов защищены входом в аккаунт; демо-посетитель видит предложение зарегистрироваться, а не ошибку.
  - **Лимит регистраций:** не больше M с одного IP в сутки (M из env). Хранилище — отдельная таблица «хэш IP + время» с удалением записей старше суток; IP в открытом виде рядом с аккаунтом не хранится.
- **Критерии (тесты):**
  - Регистрация → вход → генерация сохраняется у пользователя → после выхода и входа пост и «О бизнесе» на месте.
  - Вход при живом демо-токене — дальше работает токен пользователя; деактивированный токен вошедшего заменяется без выхода из аккаунта; суперпользователь после `/admin/` открывает генератор; после выхода демо-токена в сессии нет.
  - Пользователь B не открывает и не удаляет пост и шаблон пользователя A; демо-посетитель не видит ничьих постов; демо-посетитель на страницах профиля и шаблонов получает предложение зарегистрироваться, а не 500.
  - Выход и вход не обнуляют дневной лимит; с подменой времени лимит восстанавливается через 24 часа; при общем потолке зарегистрированный тоже получает отказ.
  - Ключ сессии меняется после входа; пароля нет в данных сессии; слабый пароль отклоняется; регистрации с одного IP сверх M отклоняются (в тестах с `LocMemCache` или БД, не `DummyCache`).
  - Страницы входа и регистрации рендерятся при `DEBUG = False`; выход GET-запросом не срабатывает.
  - `makemigrations --check --dry-run --settings=ghostwriter.settings` — без изменений.
- **Ревью:** независимый рецензент — аутентификация, правило доступа, доступ к чужим данным, миграции, хранимые данные.
