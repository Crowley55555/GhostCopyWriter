## Цель фазы

Три вещи:
1. При любой ошибке GigaChat посетитель видит понятное сообщение об ошибке, а **не** строку `WARNING: …`, выданную за пост. Ошибка не сохраняется в историю и не тянет за собой цепочку картинки.
2. Клиент картинок получает модель явно, а не берёт её из окружения через префикс `GIGACHAT_` библиотеки.
3. Поиск штампов и постобработка перестают путать штампы с обычным текстом и наоборот (замечания 2, 3 судьи по ревью фазы 2 раунд 3).

Плюс две строки-константы правил промпта из `mvp.md`, п. 5: слова клиента только из текста отзыва; в медицинских, косметологических и финансовых темах — описание услуги без гарантий результата.

### 1. Ошибка генерации — не пост

На четырёх эндпоинтах генерации (`/generator/`, `/regenerate-text/`, `/generate-image-from-text/`, `/regenerate-image/`) при любой ошибке GigaChat:

- ответ: `{"success": false, "error": "<понятное русское сообщение-константа>"}`, HTTP-код 502 или 503 (**не** 429 и **не** 500). 429 оставь только для случая, когда исчерпан лимит токена или потолок — это уже реализовано в фазе 1;
- `Generation` не создаётся и не дописывается новой версией. **Старый контракт `Generation(result="")` на пустом ответе отменяется** — записи фиксируется только успешная генерация;
- следующие вызовы цепочки не выполняются. Для `/generator/` с `generate_image=on`: при ошибке текста — ни промпт картинки, ни картинка не вызываются; при ошибке промпта картинки — картинка не вызывается. Фейк GigaChat не должен получить ни одного лишнего вызова;
- учёт фазы 1 **не меняется**: вызов, на который GigaChat ответил ошибкой, строку в `GigaChatTokenUsage` не пишет и с токена не списывается (так уже устроено — не ломай); состоявшийся вызов пишет и списывается. Это проверено ревью фазы 1 раунд 2.

Форма ответа внутри `gigachat_api.py` — на твой выбор, с обоснованием в checkpoint: исключение своего класса (`GigaChatError` или аналог) или объект-результат (`{success, text, error}`). Главное — чтобы `generator_view` и три других view могли отличить успех от ошибки, и чтобы в успешном пути никогда не возникала строка `WARNING: …`. Константа `GIGACHAT_LIMIT_WARNING` остаётся только для внутреннего пути «лимит пересечён, вызов не делаем», но в ответе пользователю её текста быть не должно: отдаётся сообщение о лимите с кодом 429 из `check_gigachat_access` или новая константа.

- **Отказ `_gigachat_limit_reached` до вызова:** возвращается сообщение о лимите с кодом 429, не пост. Вызов, пересёкший лимит, — как в фазе 1: его состоявшийся результат отдаётся пользователю, следующий вызов цепочки не идёт. Этот путь уже проверен в `tests/test_demo_access.py::CallChainAccountingTests` — убедись, что он остался зелёным.

### 2. Все `str(e)` на четырёх эндпоинтах — на константы (замечание 7)

Все пять `str(e)` в `views.py` (`:301, 421, 567, 598, 769`) заменяются на константное сообщение-ошибку (например, `MSG_GENERATION_FAILED` для текста, `MSG_IMAGE_FAILED` для картинки). Полный `str(e)` уходит только в логи через `logging.exception(...)`, не в ответ.

Это закрывает замечание 7 ревью безопасности. Строка пользователя не содержит внутренних деталей.

### 3. Фронтенд: любой текст от сервера — через `textContent`

- `gigagenerator.html:532`: обработка не-JSON ответа — текст короче 200 символов тоже прошёл обработку в `textContent`.
- **Не трогай** `gigagenerator.html:824` (имя шаблона): это задача фазы 3.
