## Вердикт

Принять после исправлений. Спецификация выполнена и хорошо покрыта тестами. Но общий дневной потолок на PostgreSQL обходится темой длиннее 255 символов (блокирует). А у края лимита токена один запрос делает до трёх неучтённых вызовов GigaChat (важно). Исправления локальные: `gigachat_api.py` и тесты.

## Замечания

### 1. Тема длиннее 255 символов выключает дневной потолок на PostgreSQL

- Серьёзность: блокирует.
- Доказательство:
  - потолок считает строки `GigaChatTokenUsage` (`generator/access.py:194-196`);
  - строку пишет `log_token_usage` с `topic=…` (`generator/gigachat_api.py:568-577`, `651-660`). Любое исключение при записи проглатывается: `except Exception: print(...)` (`gigachat_api.py:458-460`);
  - `GigaChatTokenUsage.topic` — `CharField(max_length=255)` (`generator/models.py:492-493`, миграция `0011`). На бэкенде PostgreSQL это `varchar(255)`, вывод скрипта: `PostgreSQL: GigaChatTokenUsage.topic -> varchar(255)`. PostgreSQL отвергает более длинную строку ошибкой `value too long for type character varying(255)`;
  - допустимая длина темы — 500 (`GENERATION_MAX_TOPIC_LENGTH`: `ghostwriter/settings.py:215`, `ghostwriter/production_settings.py:236`). Продакшен работает на PostgreSQL (`production_settings.py:71`);
  - тесты идут на SQLite, которая длину `varchar` не проверяет, поэтому дефект не видят;
  - эксперимент в копии. Сохранение `GigaChatTokenUsage` проверяет длину, как PostgreSQL; потолок 2. Пять POST `/regenerate-text/` с темой 300 символов → `success: [True, True, True, True, True]`, 5 вызовов GigaChat, 0 строк, пять раз `Ошибка при логировании токенов: value too long for type character varying(255)`. Контроль с короткой темой: `[True, True, False, False, False]`.
- Сценарий сбоя:
  - Посетитель отправляет тему длиной 256–500 символов. Злоумышленник — намеренно, обычный посетитель — вставив длинное описание.
  - Строку не пишут текстовые генерации (`generator_view`, `regenerate_text`) и промпт картинки в `generate_image_from_text` (тема из `last_form_data`). Потолок не растёт.
  - Лимит самого токена работает: списание идёт раньше лога. Но каждый демо-токен даёт около 7 неучтённых генераций (промпт ≈1 900 оценочных токенов плюс ответ, лимит 20 000).
  - Итог: 3 токена на IP в сутки, с десятка адресов — около 200 вызовов при потолке 50. Квота GigaChat не защищена.
- Что исправить: в `log_token_usage` обрезать `topic` (и на всякий случай `platform`) до `max_length` поля — `GigaChatTokenUsage._meta.get_field(...).max_length`. Тогда строка пишется при любом допустимом вводе. Снизить `GENERATION_MAX_TOPIC_LENGTH` до 255 недостаточно: связь двух чисел ничем не проверяется.
- Как проверить:
  - Тест с моком на уровне клиента (`_init_client`), чтобы работал настоящий `log_token_usage`. POST `/regenerate-text/` и `/generator/` с темой ровно `GENERATION_MAX_TOPIC_LENGTH` символов → строка `GigaChatTokenUsage` есть и `len(row.topic) <= GigaChatTokenUsage._meta.get_field('topic').max_length`. На SQLite до исправления падает вторая проверка.
  - При потолке 1 второй такой запрос получает 429.

### 2. Одна проверка — до трёх вызовов GigaChat; вызов, пересёкший лимит, и следующие не учитываются

- Серьёзность: важно.
- Доказательство:
  - `generator_view` проверяет доступ один раз (`views.py:196-198`). При `generate_image=on` дальше идут `generate_text` (`:205`), `generate_image_prompt_from_text` (`:221`) и `generate_image_gigachat` (`:223` или `:225`);
  - допустим, `generate_text` пересёк лимит. Тогда `consume_gigachat_tokens` возвращает `False`, и функция отдаёт строку `WARNING: Лимит токенов…` без `log_token_usage` (`gigachat_api.py:559-566`);
  - строка непустая, поэтому условие `if generate_image_flag and result` (`views.py:219`) запускает ещё два вызова. Оба тоже выходят до лога (`gigachat_api.py:642-648`, `728-734`);
  - эксперимент: токен с `used = limit − 1`, AJAX POST `/generator/` с `generate_image=on` → 3 вызова GigaChat (2 `invoke` + 1 `chat`, то есть картинка), 0 строк `GigaChatTokenUsage`. Ответ — `success: true` и `result: "WARNING: Лимит токенов GigaChat исчерпан…"`. `/generate-image-from-text/` в том же состоянии → 2 вызова, 0 строк;
  - в checkpoint (план, спорное решение 1) сказано: «Потолок недосчитывает не больше одного вызова на токен». Это неверно: до трёх, включая картинку.
- Сценарий сбоя:
  - Фронтенд шлёт `generate_image=off` (`gigagenerator.html:503-505`), но прямой запрос с `generate_image=on` у края лимита даёт 2 лишних вызова, один из них — генерация картинки.
  - Вызовы идут с уже исчерпанным токеном и без строки потолка. Это противоречит цели фазы: «ни один путь к GigaChat не работает без … лимитов».
- Что исправить:
  - (а) писать строку `GigaChatTokenUsage` для каждого состоявшегося вызова, в том числе для того, который пересёк лимит токена;
  - (б) перед каждым следующим вызовом в цепочке заново проверять лимит. Проще всего — в начале `generate_text`, `generate_image_prompt_from_text` и `generate_image_gigachat`: если токен передан и `token.can_use_gigachat()[0]` ложно, выйти без обращения к клиенту;
  - заодно решить, отдавать ли пользователю уже оплаченный квотой текст вместо `WARNING`.
- Как проверить: тест с моком на уровне клиента. Токен с `used = limit − 1`, POST `/generator/` с `generate_image=on` → ровно 1 вызов клиента и 1 строка `GigaChatTokenUsage`. Для `/generate-image-from-text/` — тоже 1 вызов и 1 строка.

### 3. Проверка токена внутри `check_gigachat_access` не покрыта тестами

- Серьёзность: мелочь.
- Доказательство: мутация в копии — ветка `if token is None:` (`access.py:186-188`) заменена на `return None`. Результат: `Ran 60 tests`, `OK`. Тесты «без токена» и «истёкший токен» отсекает middleware раньше view.
- Сценарий сбоя: фаза 3 переписывает middleware — правило для вошедших и новые исключения `/login/`, `/register/`. Если ошибка там пропустит запрос без действующего токена, единственной защитой останется эта ветка, и её поломку ни один тест не заметит.
- Что исправить: юнит-тесты `check_gigachat_access` напрямую (`RequestFactory` и сессия). Случаи: нет токена, токен истёк, токен неактивен → отказ 403 с JSON для AJAX, `request.token` не выставлен.
- Как проверить: та же мутация должна ронять новые тесты.

## Спорные решения исполнителя

1. **Расход сверх лимита в `consume_gigachat_tokens`** — согласен с тем, что расход записывается и сверх лимита: иначе токен у края ходил бы в GigaChat бесконечно.
   - Других вызовов метода, кроме четырёх в `gigachat_api.py`, нет.
   - Ветка `-1` и типы без учёта не изменились, OpenAI-аналог не тронут.
   - `can_use_gigachat` (`used >= limit`) срабатывает. Админка покажет больше 100% — без ошибки.
   - Не согласен с выводом «не больше одного вызова на токен» — см. замечание 2.
2. **JSON для AJAX в middleware и `consume_generation`** — согласен.
   - Во всех четырёх вызовах фронтенд разбирает `resp.json()` без проверки `resp.ok`, читает `data.error` и шлёт `X-Requested-With` (`gigagenerator.html:509, 551, 665, 730, 777`).
   - Обычные запросы получают прежние редиректы (`test_non_ajax_denied_redirects_to_limit_page`).
   - Ветки «нет токена» и «токен истёк» в самом `consume_generation` по-прежнему отвечают редиректом, но за middleware они недостижимы.
3. **Проверка только в ветке GigaChat** — согласен: ветка `openai` не вызывает GigaChat (идёт через Flask-клиент), у демо-токена лимит OpenAI равен 0, а саму ветку отклонит фаза 4.
4. **`current_ip` из `REMOTE_ADDR` в `start_token_session`** — согласен: поле диагностическое, проверки его не читают, поведение `token_auth_view` сохранено. Хранение открытого IP рядом с токеном — вопрос фазы 3 (ПДн).
5. **Исчерпанный живой токен не заменяется** — согласен: иначе повторное «Попробовать» сбрасывало бы лимит, а новая сессия всё равно упирается в N на IP.

## Проверено и в порядке

- **Подмена IP.**
  - В новом коде `X-Forwarded-For` не используется.
  - При `BEHIND_PROXY=False` `X-Real-IP` игнорируется; невалидный `X-Real-IP` заменяется на `REMOTE_ADDR`.
  - Старый `get_client_ip` никто больше не импортирует. `security.py` и `security_middleware.py` берут свою функцию из `ipware` и не подключены в `MIDDLEWARE`; `bot.py` её не импортирует; `manage.py check` проходит.
- **Обход middleware.** `/try/` исключён по точному совпадению. Ни одно исключение по префиксу не ведёт к эндпоинтам генерации. Ни одна из 784 вариаций пути и метода без токена до GigaChat не дошла.
- **Токены.**
  - Код, создающий `TemporaryAccessToken`, остался только в снятых view (`views.py:1257, 1585, 1915`) и в `issue_demo_token`.
  - `/auth/token/<uuid>/` только активирует существующий токен.
  - «Попробовать» выдаёт только `DEMO_FREE`: без Telegram, с лимитом OpenAI 0, на 24 часа.
- **`AccessEvent`.**
  - HMAC-SHA256 через `salted_hmac` с ключом `SECRET_KEY`, 64 символа; IP в открытом виде не хранится.
  - Записи старше 24 часов удаляются при каждой выдаче; окно подсчёта — `created_at >= now − 24h`.
  - Индексы: `(event_type, ip_hash, created_at)` и `(created_at)`.
  - Фильтр окна при подсчёте избыточен: старые записи к этому моменту уже удалены. Поэтому мутация M18 не ловится тестами; это не дефект.
- **Шаблоны.** Ни одного `{% url %}` на снятые имена. Формы содержат `{% csrf_token %}`, `landing_view` рендерит через `render(request, …)`. `subscription_tracking.js` форму не перехватывает; он шлёт клики на снятый маршрут и получает 404 — известно, фаза 4.
- **Миграции.** `0019` создаёт только `AccessEvent` и два индекса; нового дрейфа нет.
- **Настройки.** Шесть имён совпадают во всех трёх файлах, продакшен читает их из env, значения по умолчанию консервативные.

**Заметки на следующие фазы (не замечания фазы 1):**

- Фаза 6: `BEHIND_PROXY` в продакшене по умолчанию `False`. Это безопасно — все клиенты делят IP nginx, и лимит только строже. Но без `BEHIND_PROXY=True` демо закроется для всех после 3 выдач в сутки.
- Фаза 6: продакшен читает `DJANGO_SECRET_KEY`, а compose передаёт `SECRET_KEY` (п. 8 ревью версии 1). Пока это не исправлено, ключ HMAC — публичное значение по умолчанию, и хэши IPv4 перебираются. Закрывается вместе с п. 8.
- Фаза 6, гонки: кроме схемы «проверка, затем действие» есть потерянные обновления. `consume_gigachat_tokens` и `consume_generation` делают `+=` и полный `save()`, поэтому параллельные запросы одного токена теряют расход — в том числе запросы с разных IP, где `limit_conn` на IP не поможет. Нужны `F()`-выражения или `update_fields`. Строки потолка — только вставки, их это не затрагивает.
- Фаза 6: если nginx начнёт слушать IPv6, лимит N считать по подсети /64.
- Фазы 4–5: `invalid_token.html` и `limit_exceeded.html` — страницы, куда демо-посетитель попадает через сутки или после лимита, — по-прежнему ведут к боту; кнопки «Попробовать» там нет.
